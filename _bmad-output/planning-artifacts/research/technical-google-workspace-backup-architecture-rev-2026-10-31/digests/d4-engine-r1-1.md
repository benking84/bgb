# D4 Engine design lessons, round 1, digest 1

**Status: DRAFT for review.** Prepared 2026-10-31 from web sources retrieved this run. No project files were read. Engine under evaluation, as given in the brief only: fixed 100 KiB blocks, SHA-256 block IDs, zlib-compressed Duplicati-style volumes (dblock/dindex/dlist), block index in a remote database, retention plus compaction.

Source budget used: 19 tool calls, 13 distinct sources. Several WebFetch results were summarised by a helper model; quotes are as returned by that tool and should be spot-checked before client use.

## Analysis against the engine choices (for review)

Sound, with evidence:
- Packing many small blocks into volumes plus a separate index file per volume (dblock/dindex) mirrors restic packs and index files (#8). Sound in shape.
- Hash-addressed immutable blocks with SHA-256 match every engine reviewed (#1, #12).
- Retention plus compaction is standard (restic prune, Kopia full maintenance, Duplicacy fossil collection), but every one of them pairs it with an explicit concurrency guard (#9, #10, #11, #12).

Known failure patterns the brief's design overlaps with:
- **100 KiB block size** is exactly the default Duplicati abandoned in 2024 for 1 MB, citing a 10x reduction in tracked blocks (#4, #5). Borg's numbers show index cost roughly inversely proportional to chunk size (#3). For a remote index database the per-block row count drives storage, query latency and per-row cost. This is the strongest single finding.
- **Fixed-size chunking** loses dedup on inserted or shifted bytes; restic, borg, Kopia and Duplicacy all default to CDC (#1, #2, #12, #16). However, for small immutable objects (email messages) Meyer and Bolosky suggest whole-object hashing captures most savings (#19), and restic itself does not split files under 512 KiB (#1). Unverified belief, not evidenced this run: regenerated office exports (zip containers) change bytes throughout on each export, so neither fixed nor CDC chunking would dedup them well; this needs a targeted test.
- **Compaction that rewrites volumes must rewrite the index files correctly.** Duplicati's compaction bug left dindex incomplete, silently degrading recovery to "download every dblock" (#6, #7). The bug was invisible because a slow fallback masked it. Lesson: test "rebuild index from remote metadata only" as an explicit, timed check, and keep the index rebuildable rather than authoritative.
- **Keeping the authoritative index outside the backup store** (Duplicati local DB) is the root of the recreate pain. A remote DB is better than a local one, but the same rule applies: the backend files alone should be sufficient to rebuild it, and the rebuild should be exercised.
- **Compaction vs concurrent backup**: restic uses exclusive lock for prune and removes packs from the index before deleting them (#9); Kopia and Duplicacy use time or snapshot-observation grace periods (#10 to #12). An engine without one of these can delete blocks a running backup has just deduplicated against.
- **zlib** is the oldest and slowest option listed; restic, borg and Kopia all offer zstd (#17, #18). Ratio and speed numbers were not retrieved.
- **Encryption**: restic and Kopia encrypt client-side unconditionally (#15, #16); CISA guidance asks for encrypted, tested, offline-isolated backups (#14). A design relying only on provider at-rest encryption departs from all engines reviewed. No source retrieved this run directly argues the provider-admin or stolen-credential threat model; that reasoning is mine and is stated as such.
